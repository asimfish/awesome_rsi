递归自改进走到了哪一步？

从哥德尔机到自进化 agent：一次跨论文的综合判断。

先说结论

这些研究已经展示了 AI 改进自身某些组件的能力，但尚不足以证明系统能够自主、持续地提升“做下一次改进”的能力。 改写代码、优化提示、积累技能和更新权重，都可能带来真实收益；能否选择正确目标、识别有害更新，并把收益保留到新任务，仍是更难的部分。

把整个仓库放在一起看，可以提炼出三条主线：

  • 可修改的范围在扩大。 从提示与记忆，扩展到工具、执行框架、模型参数，以及产生反馈的评估器。
  • 改进是否真实，越来越难由一个分数判断。 系统既可能学会任务，也可能学会迎合评分标准；开发集进步不必然迁移到未见任务。
  • 研究正从“能不能修改”转向“该修改什么、哪些修改值得留下”。 字节三篇基准将目标形成、经验学习和执行框架改进分别拿出来测量，补上了只看最终成绩时容易遗漏的环节。

这是基于仓库所收录工作的综合判断，而非领域中所有方法都适用的定理。下面沿着这三条线说明证据与分歧。

1. 什么样的改进才算“递归”？

让模型回答得更好、让 agent 修改自己的代码，以及让系统更擅长发现和实施下一次改进，是三个不同强度的命题。

宽泛用法把“利用轨迹和反馈更新自身，并在后续任务中使用”称为自改进；更严格的 RSI 讨论还要求：一次提升能够改善后续改进的机制或能力。因此，保存了一条有用记忆，并不能单独证明递归自改进已经成立。

这一区分解释了为什么看似矛盾的说法可以同时成立：已有系统能够自改进，但开放式、持续的递归加速仍缺乏充分实证。Good 的正反馈设想和哥德尔机的形式化框架提供了问题定义；今天的工程方法主要通过实验反馈，尝试近似解决“这次修改是否值得接受”。思想史解读 · Gödel Agent 到 SICA

2. 技术路线很多，核心是改进落在哪里

改进对象 代表工作 能解决什么 新增的困难
提示、记忆与技能 WikiSkill、ACE、SkillCommit、HyperSkill 将交互经验用于后续任务，更新成本较低 信息压缩会丢掉细节；技能可能依赖具体模型或场景
harness 与源码 DGM、Meta-Harness、Self-Harness、MOSS 修改工具调用、控制流程与运行机制 补丁可能过拟合开发任务，或引入其他路径的回归
模型参数 EvoLM、ECHO、Co-Harness 将学习结果写入参数，减少对外部上下文的依赖 训练成本、负迁移与遗忘；反馈分布会随策略变化
环境与接口 EnvHarness、Continual Harness 的在线设定 改善经验获取，或在不中断任务的条件下适应 环境与验证条件的变化可能干扰效果归因
评估机制 RQGM、Who Grades the Grader、EvalCEGAR 让反馈跟上策略变化，发现原评估器区分不了的行为 谁来检查改进后的评估器，成为新的问题

这些路线可以组合。系统可以先在上下文中探索，把经验整理成技能，再通过训练吸收其中稳定有效的部分；结构性运行故障则可能需要修改源码。这里没有一条适用于所有任务的固定顺序，重要的是区分每层的收益、成本和接受条件。harness 总纲 · Co-Harness

3. 最清楚的进展：执行框架确实可以被优化

DGM 用经验评测筛选代码修改，展示了通过搜索自身 agent 实现来提高任务成绩的可能性。Meta-Harness 进一步让外部模型读取执行轨迹、诊断问题并修改 harness；Self-Harness 则研究模型修改自己框架时，回归检查能提供多少保护。

这组工作的价值在于：能力变化不只来自更换基础模型。相同模型如何获得上下文、调用工具、处理失败和决定停止，也会影响结果。但“框架可以优化”与“任意框架改动都值得保留”之间，还有一个选择问题。

作者报告的实验 观察 更稳妥的解读

Self-Harness：九个模型—基准组合均提升 带验证条件的自改写可以有效 模型能力需要与修改范围、接受规则一起评价

4. 最重要的瓶颈：分数上涨，不一定说明改进判断正确

一个系统可以同时修改解题策略和评价策略的规则。这看起来更自主，却也让分数的含义发生变化。Who Grades the Grader 的关键反例是：评估器退化后，用它训练的技能仍可能获得不错的任务分数。任务分数本身不足以证明评估器可靠。

仓库用“锚”指代进化循环之外、不随候选一起优化的评估依据，例如人工标注样本、冻结验证器或独立留出任务。它们帮助区分系统确实变好与评分标准发生漂移。但反复拿同一验证集选择候选，也会降低其独立性；最终测试、开发反馈和晋升检查需要分清。

也不能将这一经验直接写成“没有外部标签就不可能改进”。RHO 报告了基于自偏好的单轮收益，这说明无标签反馈可能有效；它尚不能回答多轮更新能否长期保持收益。因此，更值得检验的命题是：如何验证改进真实、可迁移并能持续，而不是仅要求循环成功运行。 Who Grades the Grader · RQGM · RHO

5. 字节三篇补充了什么：目标、经验和版本选择

Aspire 将评测任务隐藏，只给 agent 宽泛的能力目标。它要自己决定学习哪些数据、如何更新、如何自测。S³Gym 区分宽松探索与严格评测，检查交互历史、摘要记忆和参数学习是否改善后续决策。HarnessDev 则冻结生成的 harness，再观察它在留出任务上的表现。

它们把“自改进是否成功”分解成三个可检验的问题：目标选对了吗？经验变成策略了吗？最终留下的是有效版本吗？

HarnessDev 的反面数据尤其直接：64 次相邻版本切换中，可见反馈与留出集变化方向仅 34 次一致；九条轨迹中，只有两条声明的最终版本在留出集上最优。固定 Gemini 执行模型的四条轨迹，可见反馈均提高，但三条的留出集成绩下降。

这里可见反馈是两个基准的组合分，留出分只来自 SWE-Pro，不能把两列相减当作精确的“过拟合损失”。这些结果支持的判断是：能产生候选、能观察到局部进步、能挑选可泛化的版本，是不同能力。 字节三篇完整专题

6. 经验能积累，但积累方式决定它是否有用

WikiSkill 将证据与干预分开：知识记录持续保留，技能候选则经过验证后才采用，也可以撤回。技能进化研究进一步讨论如何组织、检索、合并和删除经验，而不只是不断追加历史。

S³Gym 提醒我们，摘要并非总优于原始历史。可压缩成通用规则的任务可能受益于摘要；依赖精确状态的任务则可能因压缩丢掉关键信息。跨模型技能迁移也可能保留有用流程，或把某个模型特有的绕行办法带给另一个模型。

因此，“拥有记忆库”还不是充分证据。需要观察经验在新任务中是否被正确使用，并与不保留经验、保留原始历史等对照比较。长期记录的价值也包括保存失败原因，避免系统重复提出已经被否决的更新。WikiSkill · 技能进化五篇

7. 从实验到生产，还缺什么？

生产系统关心的不只是最高分，还包括失败时能否恢复、修改能否解释，以及服务是否持续可用。MOSS 的源码更新流程和 Reef 的运行基础设施，将候选评估、版本记录与回滚变成了系统的一部分。

这解决的是执行和管理问题，不能替使用者定义正确目标。评估门即使做成了组件，门里使用什么指标、覆盖哪些失败、谁有权放宽约束，仍需单独决定。芯片设计是一个具体例子：优化时延或面积之前，要先守住功能正确性；工具给出的局部指标还要结合工艺、约束和验证范围解释。MOSS · Reef · 芯片专题

同样，某一步实验加速或代码产出增加，不能直接推出整个研究过程按同样比例加速。方向选择、真实实验、外部反馈和最终判断，仍可能决定端到端速度。产业证据与论文基准应分开阅读，也应区分作者披露与独立验证。产业进度解读

8. 下一步最值得回答的五个问题

  1. 怎样选择目标？ 当任务和评分不再由人明确给出，系统能否构建与真实需求一致的代理目标？
  2. 最少需要多少独立评估？ 在有限标注和测试预算下，如何及时发现评估器漂移或有害修改？
  3. 经验何时能够迁移？ 哪些知识应保留原始记录，哪些可以压缩成技能，哪些值得写入参数？
  4. 如何选择和保留版本？ 当开发反馈与真实效果不一致，停止条件、回滚规则和候选选择怎样设计？
  5. 改进机制本身有没有变强？ 必须把“多尝试了几轮”与“更擅长发现下一次改进”分开测量，才能讨论更严格的递归自改进。

这几条问题把仓库中的模型、harness、技能、评估和治理研究连在了一起。已有结果让局部自改进成为可研究的工程问题；持续、可验证的改进能力，则仍需要更好的实验来建立证据。
