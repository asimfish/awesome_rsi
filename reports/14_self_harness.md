## 1. 一句话定位

harness 设计天然是**模型特异**的——不同模型的工具使用习惯、错误模式、prompt 敏感性各不相同——靠人类工程师逐模型手调不可持续，靠更强外部 agent（Meta-Harness 范式）又贵、对前沿模型不可得、且可能与目标模型的失败模式错位。Self-Harness 让**同一个冻结模型**在当前 harness 下运行、被评估、然后自己扮演 proposer 给自己的 harness 提出有界编辑；三阶段循环（弱点挖掘 → 并行提案 → 双 split 回归验证）在 **3 模型 × 3 基准全部 9 个组合**上同时提升 held-in 与 held-out 通过率，无一晋升 harness 令任一 split 退化。最大相对增益 **Qwen3.5-35B-A3B 在 AppWorld +132%（22.5→52.2）**，最大绝对增益 **GLM-5 在 AppWorld +40.6pp（44.4→85.0）**。它是 harness 谱系的第三范式（人工工程 → 外部强 agent 优化 → 固定模型改自己的 harness），也是对 Continual Harness"能力地板"论最直接的正面挑战——35B 级弱模型走通了自改进循环，靠的不是能力，是**接受门**。

## 2. 要解决的问题

论文的出发点是一个被 Meta-Harness 放大的矛盾：harness 对性能影响巨大且模型特异，但两条现成路线都有结构性缺陷。

**人工工程**：Terminus-KIRA、ForgeCode 等 SOTA harness 全靠工程师看失败轨迹、调 prompt、加工具、迭代——每换一个模型（或同一模型换版本）都要重来，且工程师的直觉未必对齐目标模型的真实失败分布。

**外部强 agent 优化**（Meta-Harness）：用 Claude Code + Opus 做 proposer，每轮读 10 MTok 原始轨迹——三个问题：(i) **贵**，三个数量级的反馈消费；(ii) **对前沿模型不可得**，如果目标模型本身就是最强的，没有"更强的外部 agent"可用；(iii) **失败模式错位**，外部 proposer 对目标模型的工具习惯、prompt 敏感性没有第一手经验，改出来的 harness 可能适合 proposer 自己而非目标模型。

Self-Harness 的命题：**能不能让被优化的模型自己做 proposer？** 这立刻引出两个反对：弱模型消化不了全历史（Meta-Harness 消融证明摘要会丢信号）；弱模型自改可能改坏（Continual Harness 发现 Flash-Lite 之下自改进全线更差）。论文的回答是两个工程手段——**证据压缩**（弱模型只见结构化失败签名，不见原始日志）和**回归门**（改坏即拒，不进 lineage）。

## 3. 为什么此前做不通：三条线各差一块

| 已有路线 | 有什么 | 缺什么 |
|---|---|---|
| Meta-Harness（报告 13） | 前沿 proposer + 全历史文件系统 | proposer ≠ 目标模型；贵；前沿模型无更强外部 agent |
| Continual Harness（报告 11） | 免重置、故障现场精炼 | 精炼直接进下一步上下文、**改坏照单全收**；Flash-Lite 之下全线更差 |
| DGM（报告 07） | 改自身源码、种群档案 | 每步评估全 SWE-bench 子集，成本高；改的是 agent 代码本身而非声明的可编辑面 |
| AutoSaddler（报告 16） | 离线 mini-batch 更新 harness | 需要泛化门；无失败签名聚类 |
| prompt 优化器（GEPA、OPRO） | 迭代改 prompt | 只改 prompt 不改工具/中间件/验证策略；无回归门 |

关键缺口：**没有人证明"目标模型 = proposer"这个闭环在弱模型上能走通**。Continual Harness 的能力地板论说不能；Self-Harness 说能——差别在接受门。这是全调研关于"弱模型能否自举"最重要的一组对照证据。

## 4. 方法机制

### 4.1 形式化

模型 M 与评估器 E 全程冻结；harness h 是被改进的对象。Self-Harness 在 harness lineage h_0, h_1, … 上操作，每次转换是对执行协议的**有界编辑**，而非权重更新。因为 M 和 E 不变，跨轮的记录变化可以归因于 harness 变化。

### 4.2 Weakness Mining（弱点挖掘）

在 held-in 集 D_in 上跑当前 h_t，每个任务产出 (x_i, τ_i, y_i, z_i)——任务、轨迹、输出、verifier 判决。对失败记录 F_t 提取 **verifier 锚定的失败签名**：

φ(r_i) = (c_i, q_i, m_i)

c_i = 终端 verifier 级失败原因（超时、缺产物、断言失败）；q_i = 相关 agent 行为的因果地位；m_i = 轨迹暴露的抽象 agent 机制。**按签名精确一致做确定性聚类**——刻意不做语义相似聚类，只聚"可能吃同一个 harness 干预"的失败。两次超时可能因为不同行为机制而分属不同簇。

每个簇构造结构化失败模式（簇大小、代表任务、共享轨迹症状、verifier 证据、推断的 agent 机制），按支持度与可操作性排序。输出**证据包 B_t**——它**不规定 harness 编辑**，只把 verifier 级失败与 agent 级机制分开，让 proposer 瞄准可复用的弱点而非粗粒度结果。

### 4.3 Harness Proposal（并行提案）

同一模型 M 被以 proposer 身份调用，输入是**有界提案上下文**：可编辑面、失败模式、需保留的成功行为、历史提案摘要——**不是原始日志**。并行产出 K 个互异提案 (Δ_j, a_j)，每个附审计记录（目标失败模式、编辑面、预期行为效果、回归风险）。

**可寻址性判据**：不是每个失败簇都值得修——有的反映任务特定难度、结果不稳定、纯能力上限。proposer 优先选具体、反复、可通过窄改动缓解的机制；弱支持或不可寻址的簇**明确排除、不硬补**。

**分支间多样、分支内极小**：不同分支可以瞄准不同机制、不同 harness 面、不同假设；但每个编辑只改选定机制所需的面、保留无关行为、**禁止重写控制架构**。

### 4.4 Proposal Validation（回归验证）

候选 h_t^(j) 在 D_in 与 D_ho 双 split 重评，接受当且仅当：

Δ_in ≥ 0 且 Δ_ho ≥ 0 且 max(Δ_in, Δ_ho) > 0

拿一边换另一边的提案即使总分升也拒绝。评估有随机性时重复并按聚合计数套用同一规则。同轮多个通过则合并进 h_{t+1}；被拒的留日志但不改活跃 harness。每笔转换记录改动面、双 split 结果、重复次数、提案摘要、接受理由——**全谱系可审计**。

### 4.5 与 Meta-Harness 的镜像差异

那边 proposer 自由读 10 MTok 原始轨迹；这边 proposer 只见压缩证据包——因为这边的 proposer 就是被优化的弱模型本身，喂不动全历史。Meta-Harness 消融证明摘要丢信号，Self-Harness 靶向的是另一个问题：**在信息带宽受限时，怎样让每一步编辑至少不变坏**。

## 5. 实验结果全景

### 5.1 设置

- **初始 harness 极简**：DeepAgent SDK + 短 system prompt（"你在 Terminal Bench 2 环境里，用内建文件系统与 shell 工具检查、编辑、验证；不要假设合成数据集或隐藏 fixture"）+ 文件/shell 工具，Figure 3 全文不到 60 行。可编辑面是声明的配置点（instruction、工具、验证指引、中间件等）。
- **模型**：MiniMax M2.5、Qwen3.5-35B-A3B、GLM-5；同一模型做 proposer。
- **基准**：Terminal-Bench-2.0（64 题子集，排除依赖不稳定外部网络或多模态的任务）、SWE-bench Verified（100 题：67 held-in / 33 held-out，按仓库比例采样）、AppWorld（180 题：90/90；held-in 是官方 train，held-out 从 test_normal 与 test_challenge 比例采样）。
- **指标**：Pass (%)，每候选评 **2 次**取均值。

### 5.2 主结果（Table 1）

| 模型 | 基准 | 初始 | 最终 | 相对 | held-in→ | held-out→ |
|---|---|---|---|---|---|---|
| MiniMax M2.5 | TB2 | 42.2 | **53.9** | +28% | 43.0→50.0 | 40.5→61.9 (+53%) |
| Qwen3.5-35B | TB2 | 18.0 | **36.7** | +104% | 15.1→36.0 | 23.8→38.1 |
| GLM-5 | TB2 | 46.1 | **57.0** | +24% | 47.7→57.0 | 42.9→57.1 |
| MiniMax M2.5 | SWE-V | 46.0 | **52.5** | +14% | 51.5→58.2 | 34.8→40.9 |
| Qwen3.5-35B | SWE-V | 19.5 | **41.5** | +113% | 20.1→42.5 | 18.2→39.4 |
| GLM-5 | SWE-V | 52.0 | **55.5** | +7% | 53.7→58.2 | 48.5→50.0 |
| MiniMax M2.5 | AppWorld | 48.6 | **58.9** | +21% | 51.7→62.8 | 45.6→55.0 |
| Qwen3.5-35B | AppWorld | 22.5 | **52.2** | **+132%** | 25.0→60.0 | 20.0→44.4 |
| GLM-5 | AppWorld | 44.4 | **85.0** | +91% | 47.8→92.2 | 41.1→77.8 |

**9/9 双升**。4/9 组合的 held-out 相对增益反超 held-in（MiniMax 与 GLM-5 在 TB2、MiniMax 与 Qwen 在 SWE-V）。弱模型（Qwen 35B-A3B）相对增益最大——起点低、可修的 harness 级失败多。

### 5.3 进化轨迹（Figure 4）

**Qwen3.5 on TB2**（18.0→36.7，20 次候选评估）：接受链——"迟交付 → artifact-ensure 子代理"（31.3）、"跳过 import → 依赖验证器技能"、"缺模块 → 预检 import"（34.4）、"探索循环 → 强制变更"、"缺文件 → 2 步内创建"、"工具错误 → 中间件守卫"（36.7）；中间穿插多个被拒分支（21.1、24.2、32.8）。

**MiniMax on TB2**（42.2→53.9，15 次）："缺产物 → 尽早创建输出"（49.2）、"工具循环停滞 → 50 次工具调用后重定向"（50.0）、"schema 无效内容 → 正确内容标签"（51.6）、合并三者（53.9）。

**MiniMax on SWE-V**（46.0→52.5，9 次）："空补丁 → diff 检测器"（50.0）、"更严测试策略 → 本地测试强制"（51.0）、"未测补丁 → 本地验证"（52.5）。

**GLM-5 on AppWorld**（44.4→85.0，13 次）："action-only 任务 → null 完成语义"（**76.4**，单步 +32pp）、"turn 预算耗尽 → 进度检查提醒"（67.2，被拒）、"部分记录列表 → 分页穷尽"（74.7）、合并完成语义 + 分页（85.0）。

### 5.4 留存编辑高度模型特异

同一失败大类在三个模型上收敛到三种不同实现：

- **MiniMax**：bootstrap 指令从"找最小编辑面"改为"找必需输出产物并尽早创建初版"；启用工具消息总数上限打断空转；结构化内容标签。轨迹对比（count-dataset-tokens 任务）：从长时间数据集探索变成"定位元数据 split → 算计数 → 写 answer 文件 → 读回验证 → 停"。
- **Qwen**：依赖预检、循环打断、命令重试纪律、工具错误触发的产物恢复中间件。轨迹对比：初始 harness 下创建 extractor 脚本后遭遇覆盖/编辑失败、反复改同一产物、最终**删掉 /app/extract.js** 后停止（verifier 因缺文件判失败）；编辑后 harness 的工具错误触发 system prompt 把 agent 重定向到缺失产物，重建、修解析、写输出、定向验证 JSON。
- **GLM-5**：环境变更跨 shell 会话持久化、修改环境后验证工具可达、"探索够了就转实现"。轨迹对比（构建任务）：初始版在长外部下载上耗预算、事后为失败的 sanity check 找理由；编辑版在超时证据后切换策略、早验证替代源、修渲染检查再收尾。

这正是"harness 必须模型特异"论点的实证——也是 Meta-Harness 范式（外部 proposer 改出通用 harness）不能完全替代的原因。

## 6. 局限

1. **held-out 并不真 held-out**。晋升门显式消费 held-out 增量非负这一条件——held-out 分数是选择信号的一半，它是**回归门而非终检**。多轮循环下这构成对 33/90 题小集合的多重假设检验；"9/9 双升"部分是接受规则的构造保证（不双升就不晋升），据此宣称泛化需打折。**进化全程从未参与任何决策的第三方锚集不存在。**
2. **统计功效薄**：每候选只评 2 次、split 只有几十题，pass 计数差 1–2 就能翻转接受决定；论文提到随机时"重复并聚合"，但未报告方差或显著性检验。
3. **无跨基准迁移测试**：TB2 上进化的 harness 只在 TB2 两个 split 验证，作者自认留存编辑"可能仍反映基准特异的失败模式"。
4. **TB2 只用 64/89 题**——排除了多模态与不稳定网络任务，与 Meta-Harness 的 89 题不可直接比。
5. **论文自我定位诚实**：这是固定基准下的有界编辑研究，不是开放式自改进；更高风险的 harness 变更需要比"通过率不回归"更强的接受门——这句自白恰好呼应 MOSS（报告 08）的门控设计动机。
6. **proposer 与被优化模型同一**：理论上 proposer 可以学会"改 harness 让自己在 held-in/held-out 上过关"而非真正改善——但因为 E 冻结且是官方 verifier，这种 gaming 空间比 LLM-judge 场景小得多。

## 7. 意义与位置

**对报告 13（Meta-Harness）**：论文 Figure 1 直接把两者摆成范式对照——外部强 agent 优化 vs 自我优化。二者互补而非替代：Meta-Harness 靠前沿 proposer 满血反馈拿绝对上限（TB2 榜第 1/2），Self-Harness 靠"证据压缩 + 回归门"让 35B 级模型也走通循环。代价镜像：前者天花板系于外部 proposer，后者的证据包压缩恰是 Meta-Harness 消融证明会丢信号的那类摘要——**弱模型自改进的信息带宽被自己的上下文消化能力锁死**。

**对报告 11（Continual Harness 能力地板）**：CH 里 Flash-Lite 之下所有自改进变体全线更差，本文 Qwen3.5-35B-A3B 却 +104% 至 +132%——表面矛盾，机制解释是**接受门**：CH 的精炼直接进下一步上下文、改坏了照单全收；Self-Harness 每笔编辑都过回归测试、改坏即拒。**锚定纪律本身就是地板保护**——这是全调研关于"弱模型能否自举"最重要的一组对照证据，也说明"能力地板"不是模型的固有属性，而是"模型 × 接受机制"的联合属性。

**对报告 05（WGtG 锚定纪律）**：评估器 E 与模型 M 全程冻结、只动 harness，是标准锚定姿势；失败签名由 verifier 结果锚定而非语义聚类，把"评估器不参与进化"贯彻到了诊断层。但如上所述，held-out 进入晋升规则让锚变薄了一层——**锚的位置对了，锚的独立性没守满**。

**对报告 07（DGM）与 08（MOSS）**：harness 谱系 h_0 到 h_T 每步转换均有审计记录，是 DGM 档案思想的**线性化轻量版**（合并接受编辑，放弃种群分支与回溯）；"回归测试通过才晋升"与 MOSS 的门控发布同构——文本/配置层的自改进安全纪律已经趋同：**有界编辑面 + 不回归门 + 可审计账本**。

**对报告 09（WikiSkill）**：留存编辑的模型特异性（同一失败、三模型三种修法）反向支持 WikiSkill 的前提——经验资产要针对消费它的模型编译；通用 harness 资产（Meta-Harness 的可迁移 harness）与模型特异 harness（本文）大概率构成资产市场的两层：前者做底座，后者做适配层。

**对报告 16（AutoSaddler）**：两者都是"有界编辑 + 门控"范式，AutoSaddler 的泛化门消融显示没有门时收益为负——与 Self-Harness 的回归门必要性互为印证。
