# EvalCEGAR 深度解读：让评估器从自己的盲点里长出来——碰撞对是最有信息量的锚样本

> **EvalCEGAR: Evolving Evaluation Metrics from Their Own Blind Spots via Counterexample-Guided Refinement**
> arXiv 2608.18744 v1（2026-08-19）· AWS Generative AI Innovation Center（Xing Zhang、Yanwei Cui、Guanghui Wang、Zhihao Lin、Peiyang He†）
> 归档：`papers/en/2608.18744_EvalCEGAR.pdf` · 中译 `papers/zh/2608.18744_EvalCEGAR_zh.pdf`
> 同团队前作：Who Grades the Grader（arXiv 2607.12790，报告 05）

## 1. 一句话定位

自改进系统先需要度量、后需要策略：有可靠自动度量时 agent 提升飞快，没有时就停摆，而最需要度量的应用（报告生成之类）恰恰没人知道怎么打分。本文问：**度量能不能自己写自己？** 答案是可以，但不能靠"让模型写一个评估算子"——那样 **183 个候选只实现 96 种不同行为**，全部挤在巨大空间的一个狭窄角落，295 个算子零发现。EvalCEGAR 把算子池当作一个**抽象**（每个候选答案 → 池子的判决向量 = 签名），搜索**碰撞**：两个答案签名相同、却一对一错——这一对（而不是一个 prompt）就是编写请求，它**证明**了当前度量无法表达这个区分；每次准入重新划分签名空间，下一条规格在构造上就不同，**多样性压力来自目标而非采样器**；当一个碰撞击败所有尝试时，循环**放宽算子可读取的信息**而不是重新采样。MBPP+/HumanEval+ 上：循环写出一个 **55 行**算子，在 428 个未见任务上关闭 **15.4% 的可达差距**（+0.0065，p = 0.0010），flag 数只有最强手写算子的四分之一；八次运行六次准入，**六个全部在样本外有效**；反面对照：作者 **15 个手写算子合起来当过滤器，准确率反而下降**。它是 Who Grades the Grader 的直接续作：报告 05 证明必须外置锚；本文回答"有了锚之后，评估器本身怎么进化"——这是全谱系里**锚利用效率最高**的设计。

## 2. 要解决的问题

论文的问题陈述由两次失败的实验定义（"我们先跑了显然的循环：让模型写一个算子、门接受就留、重复"）：

**障碍 1 · 算子空间巨大，模型只采样一个微小的固定区域**。被要求"写一个评估算子"的模型每次给出的东西高度相似——重采样不会移动那个区域。给全部 295 个在狭窄接口下写出的算子打分，零发现。

**障碍 2 · 写出来的东西行为上互相重复且大多被拒**。五次运行 183 个算子只实现 96 个不同 flag 集。更糟的是**一次拒绝什么都教不了**：循环只知道候选失败了，不知道它没画出哪条区分线——下一次采样与上一次无关。

背后的形态学选择：度量 = **算子池投票**。每个算子是一个小 Python 函数 o(t, y) → {flag, clean, abstain}，对某个具名缺陷做三选一；足够多成员 flag 就拒绝该候选。这个形态利用了一个在没有参考答案时仍成立的不对称性：**说一个答案有多好需要一个没人写下来的标准，指出它哪里错了通常不需要**。每个算子只陈述一条反对意见，因此可以单独被读、被运行、被证伪；池子的有效性是被测量出来的属性——**每个成员都必须先在下游决策上挣到位置才能加入**。

## 3. 为什么此前做不通：三条线各差一块

| 已有路线 | 有什么 | 缺什么 |
|---|---|---|
| 学习型度量 / LLM judge（BERTScore、G-Eval） | 不需要手写 rubric | 输出是**单一标量**，读者无法拆分；不可证伪；每候选一次模型调用 |
| rubric 分解 + 冗余过滤 | 更细的判据 | 仍是标量；judge 与 solver 共享失败模式 |
| FunSearch / ADAS 程序搜索 | LLM 写程序 | 针对**给定**评估器进化程序——本文是补集：评估器本身是工件，没有固定 fitness |
| LLM 写 Python 验证器 + 组合 | 可执行检查 | 搜索**预测标签的检查**；本文搜索**证明当前检查不能预测的反例** |
| Quality-Diversity 搜索 | 显式行为档案防塌缩 | 多样性来自档案维护；本文来自目标重划分——§6 测了这买不到什么 |
| Who Grades the Grader（报告 05） | 锚定纪律 + 表达式树 | 锚只用于**检验**；本文把锚用于**驱动** |

关键缺口：**没有人把"当前度量的盲点"作为下一个算子的规格**。既有方法的多样性靠采样器（温度、档案），EvalCEGAR 的多样性靠目标——每准入一个算子，签名空间重新划分，剩下的碰撞对就是新的、构造上不同的规格。

## 4. 方法机制

### 4.1 CEGAR 借来的纪律

程序验证里的 counterexample-guided abstraction refinement：只有当一个具体反例证明当前抽象太粗时才精化抽象。EvalCEGAR 的映射：

- **抽象** = 算子池，把每个候选答案映射成**签名**（池子对它返回的判决向量）；
- **反例** = **碰撞**：签名相同、ground truth 不同的一对答案——它**证明**了度量无法表达这个区分；
- **精化** = 把这一对交给模型作为规格，写一个能区分它们的新算子；
- **准入** = 只有当新算子**改善部署决策**（selection accuracy）时才加入——不是"覆盖更多已知缺陷"。

### 4.2 循环

1. 用当前池给训练 split 的候选答案打签名；
2. 找碰撞类 C = {签名类同时含 y=1 与 y=0 的候选}——这些是盲点；
3. 取一个碰撞对交给模型：写一个算子，使这两个答案签名不同；
4. 候选算子过四道 screen（不读 oracle、不重构 oracle、…），再测**准入问题**：加入后 selection accuracy 是否上升；
5. 准入 → 签名空间重划分 → 回到 2；
6. 当一个碰撞对击败所有尝试（预算耗尽），**放宽接口到 level-2**（算子可读更多信息，如执行轨迹）——一条当前接口下无法画出的区分线，靠更多样本也画不出。

### 4.3 锚只进训练集

ground-truth 标签只在训练 split 的两处读取（碰撞检测与准入判定）；held-out 全程不读；部署后算子**零模型调用**。75 个训练任务里只有 **10 个**同时含存活可见检查的正确与错误候选——这就够准入可迁移的算子。

## 5. 实验结果全景

### 5.1 设置

MBPP+ / HumanEval+（EvalPlus 隐藏单元测试 = 精确 oracle）。150 个 MBPP+ 任务对半分：75 跑循环、75 held-out；再加 228 个剩余 MBPP+ 与 125 个 HumanEval+ 到 held-out——共 **428 个未见任务**（HumanEval+ 是唯一不同分布的组）。

**Selection accuracy**：对每个任务采样多个模型解，V(t) = 通过可见检查的候选（部署系统会接受的）；度量 flag 一部分、从剩余 K(t) 均匀抽一个；抽到正确的概率。**只有 58/428 任务是可判定的**（V(t) 同时含对错），所以 selection accuracy 从"什么都不 flag"的 **0.7170** 到"完美过滤"的 **0.7593**——绝对 Δ 天然很小，论文同时报**headroom 百分比**。

**对照**：15 个手写算子（10 静态 AST 检查 + 5 执行）合成的人类基线；最强单算子 **comparator**（flag 与同任务其他样本多数行为不一致的候选）；LLM judge。

### 5.2 主结果

| 指标 | 数值 |
|---|---|
| 最佳算子 | 55 行 Python |
| 428 未见任务 Δ | **+0.0065（p = 0.0010）**，关闭 **15.4% headroom** |
| flag 数 vs 最强手写算子 | **1/4** |
| 八次运行准入 | 6 次；**6/6 样本外有效** |
| 第二基准（未见） | 用 **1/3** 的 flag 精确复现最强手写算子的效果 |
| 15 个手写算子合用 | **准确率下降**——人写检测器堆在一起互相抵消 |
| LLM judge | 同信息上追平 Δ，但命中**几乎不相交**的候选集，且每候选一次模型调用 |

### 5.3 机制消融（§5.2，相同信息）

- **准入问题**（"是否改善部署决策"vs"是否覆盖已知缺陷"）：单独把准入从 0 变成 1；
- **窄接口**：336 次尝试零准入——level-2 放宽是必要的逃逸；
- **碰撞目标 vs 自由采样**：183 个自由采样算子 96 个不同行为；碰撞目标每次规格构造上不同。

### 5.4 组合精确求解（§5.3）

穷举循环能组合的全部 **230 万个子集**：循环用来组合它们的目标（投票）排在该空间的 **第 5 百分位**，一个未调参的类加权目标排在 **第 91 百分位以上**——组合方式是当前设计的明显短板。

## 6. 局限

1. **绝对增益很小**：+0.0065、关闭 15.4% headroom——统计显著但工程上微弱；论文贡献在方法论（碰撞对作为规格）而非效果规模，作者对此坦诚。
2. **仍然依赖精确 oracle**：MBPP+/HumanEval+ 之所以被选，正因为隐藏测试给出精确 ground truth；论文开篇说最需要度量的是报告生成这类无参考任务，但实验没有触及它们——**碰撞检测在没有 oracle 的域里如何定义**，是全文回避的问题。作者的辩护是"在真值已知但被隐藏的地方验证方法"，成立但不完整。
3. **算子表达力受接口限制**：level-2 放宽接口是唯一逃逸机制，但放宽到什么程度、放宽后算子是否退化为 LLM judge，没有讨论。
4. **与 LLM judge 的互补性被低估**：两者命中几乎不相交的候选集，暗示最优方案是组合，而非算子替代 judge。
5. **投票组合排第 5 百分位**——论文自己发现的，但没有修。
6. **只有 58/428 可判定任务**——headroom 太小让结果对采样深度敏感。

## 7. 意义与位置

**报告 05 的正面延续**：Who Grades the Grader 的结论是"没有进化外的锚就无法区分塌缩与进化"；本文把锚的用法从"检验"推进到"驱动"——碰撞对是锚上最有信息量的样本，评估器进化的每一步都由锚上的失败精确指向。WGtG 用十条锚做**守卫**，EvalCEGAR 用十个碰撞对做**规格**——同一团队一年内把锚的角色从被动变主动。

**与 EvoLM（报告 03）的对照**：EvoLM 让 rubric 生成器与 policy 在权重层共进化、依赖 RL 信号；EvalCEGAR 的度量是可读可证伪的 Python，进化过程完全离散且可审计——两条路线在"评估器要不要可解释"上分道。EvoLM 的 rubric 是文本、可读但不可执行；EvalCEGAR 的算子是代码、可读且可执行。

**与 RHO（报告 25）的对极**：RHO 干脆不要外部评估器，全靠自偏好；EvalCEGAR 把外部 oracle 当作不可替代的规格来源。两篇同在 2026 年 6–8 月发表，是评估器战争里"锚的最小化"与"锚的最大化利用"两个极端。

**与 RQGM（报告 04）**：RQGM 的锚数据集用于**晋升判定**（挑战者是否比在位者好）；EvalCEGAR 的锚用于**生成规格**——RQGM 若把锚上评估器判错的样本当作下一轮 evaluator 的编写请求，就是 EvalCEGAR。

**对报告 10 开放问题 1（最小锚问题）的贡献**：本文给出一个数据点——428 个未见任务上有效的算子，训练时只需要 10 个碰撞对级别的标签消耗；"需要多少锚"第一次有了可以计数的单位（碰撞对数）。

**对报告 26 技能进化**：SkillProx 的"删除一等公民"与 EvalCEGAR 的"准入必须改善决策"是同一纪律在不同对象上的实例——技能库与算子池都会因为无门槛累积而互相抵消（15 个手写算子合用反而下降）。
