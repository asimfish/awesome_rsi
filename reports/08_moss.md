## 1. 一句话定位

MOSS 是六篇核心中**唯一覆盖生产部署**的方案：把源码级自改写从学术最小脚手架搬到承载真实用户流量的生产 agent 系统（OpenClaw），配全失败证据驱动、试用容器重放、用户批准门控和自动回滚。它的立论是：现有自进化 agent 全部把进化范围限制在**文本可变层**（skill 文件、prompt、记忆、工作流图），而路由、hook 顺序、状态不变量、分发逻辑住在**代码**里——这一整类结构性故障从文本层物理上不可达；MOSS 论证源码级适应是严格更一般的媒介（图灵完备、文本层的严格超集、确定性生效、不随长上下文漂移而衰减），并在生产级底座上实现它：单轮进化把四任务平均评分从 0.25 提到 0.61，全程无人工介入。

## 2. 要解决的问题：文本可变层的物理边界

论文的出发点是一张范围对照表：Hermes Agent 进化 skill+记忆、SkillClaw 进化 skill、GenericAgent 进化 skill+记忆、EvoAgentX 进化 skill+prompt——**没有一个碰 harness**。文本层编辑只能改变"agent 自己怎么想"（说什么、调哪个 skill、怎么拆子目标），改变不了"harness 替它做的决定"。一旦故障源于 harness——消息误路由、hook 乱序触发、会话状态损坏、并发 skill 的原子性 bug——任何 prompt/skill/记忆更新都够不着。且这类故障的占比随 harness 复杂度上升，系统越成熟缺口越大。

**源码级适应优于文本级的四条论证**：
1. **图灵完备**：源码设计空间是全域搜索空间，每个文本可变空间（prompt、skill、记忆模式、工作流图）都是它的严格子集；
2. **严格超集**：prompt 能做到的，等价代码编辑都能做到，反之不然；
3. **确定性生效**：路由逻辑、hook 顺序、状态机不变量作为代码运行，不依赖基础模型"正确读到新文本并遵守"——文本修复的有效性随模型能力浮动；
4. **不随时间衰减**：文本修复要求 agent 每轮重读，数周生产使用后遵守度被累积内容稀释；源码层编辑被编码为行为而非待读文本，系统老化不降级。

这四条构成对 EvoLM/WikiSkill 一类"文本层进化"路线的正面批评，也是对 Weng "harness 是可执行搜索空间"论断的生产级注脚。

## 3. 为什么此前做不通：与学术线（DGM 系）的分界

作者对相关工作的切分干净利落：**学术线**（SICA、DGM、HyperAgents、Meta-Harness）在最小脚手架上证明了源码自改写可行，但反馈全部由基准分数门控——本质是**探索式范式**：按分数随机变异、留优汰劣。这个范式不能迁移到生产系统，原因有四：代码库太大，无向变异几乎不会落在有用的改动上；生产 agent 的质量是任务特定的，没有基准式全局适应度信号；在真实用户流量下，无锚定的补丁与回归无法区分；用户期望**他们遇到的那个场景被修好**，而不是 agent 被全局重调。

MOSS 因此改用**定向确定性范式**：每次进化锚定到一批具体的生产失败证据，所有下游阶段都绑定"修好这批"——这是把 RQGM 的"非平稳效用"问题用工程手段落地：不追求全局适应度，只追踪真实用户暴露的具体缺陷。

## 4. 方法机制

### 4.1 系统架构（五件套）

1. **主容器（moss-gateway）**：跑用户侧 agent + 容器内进化服务 + bind-mount 的 moss CLI；
2. **控制面 CLI**（`moss evo`，9 个子命令）：agent 通过自带 shell 工具调用，用户用日常对话界面驱动进化（触发、查状态、停止、批准、标记不满意的轮次）；能力文档按需读取，webhook 反向通知（收敛/失败/换装完成）作为系统消息送达 agent 下一轮。任何提供 5 个原语（shell 执行、文件读、定时调度、webhook 送达、系统提示注入）的底座都能承载 MOSS，无需改 MOSS 代码；
3. **可插拔外部编码 agent CLI**：代码修改委托给宿主机子进程（Claude Code / Codex / DeepSeek-TUI / OpenCode 四个 runner 内置，四方法接口，加新 provider 只需一个 runner 文件）——MOSS 保留阶段排序与裁决权，编码 agent 只在给定范围内负责"编辑"这个动作；
4. **宿主机守护进程（host-daemon）**：容器生命周期不能住在主容器里（进程退出后无法再启动新容器），故换装监督、试用容器编排、docker 构建、自动扫描引擎全在宿主机 asyncio 进程中；
5. **临时试用容器（trial workers）**：每轮迭代从候选镜像起 N 个短命容器，网络与挂载全隔离，agent 在其中自主重放失败批次（每任务多次试验暴露不稳定性），跑完即拆。

### 4.2 进化流程

**证据采集（两条通道汇入同一批次）**：定时 cron 跑 `catch-up` 扫描所有会话 JSONL，按游标切块，Task-Evaluate 阶段给关键点打分，弱/缺失的块进当前开放批次；用户在对话中表达不满时 agent 调 `flag` 做同样扫描。每会话维护一个开放批次，满 8 块封存。

**迭代循环**：先跑基线评估（对批次里已捕获的原始转录打分，产出基线关键点矩阵，**关键点集就此锁定**）；然后每轮跑七阶段流水线，以四裁决之一结束——CONVERGED（收敛，出循环）、NEED_MORE_WORK（继续）、FUNDAMENTAL_LIMIT_MODEL（模型天花板）、FUNDAMENTAL_LIMIT_ARCHITECTURE（架构内无解）。平台期守卫：连续数轮无关键点改善则在当前峰值强制收敛。进化深度旋钮（light/standard/deep）统一缩放迭代预算。

**七阶段流水线**（每阶段调用一次编码 agent CLI，各读不同工件）：
1. **Locate**——读基线痕迹与批次失败，只写诊断不提修复；
2. **Plan**——定位根因、指定修复（改哪些文件、加什么逻辑、不动什么）；
3. **Plan-Review**——第一道质量门（批准/架构跑偏/范围过窄），与 Plan 多轮交替至批准或预算耗尽；
4. **Implement**——在内层底座仓库落为单个 git commit；
5. **Code-Review**——第二道质量门，diff 对照计划审查，轮间硬重置工作树；
6. **Task-Evaluate**——构建+试用重放后，按四级定性量表（strong/adequate/weak/missing）给每任务 4-7 个关键点打分；
7. **Verdict**——综合逐任务评估与跨迭代关键点矩阵给出裁决。

**运行时验证的理由**：Code-Review 只在语法语义层工作，竞态、跨模块状态交互、hook 顺序依赖行为只在运行时显形——所以验证必须在生产等价环境、用产生失败证据的同一批 prompt 重放，而非单元测试或外部基准。

**就地容器换装**：收敛**不自动晋级**——发 webhook 通知用户，等待 `moss evo apply` 显式批准；批准后守护进程重启容器到候选镜像，90 秒探测窗（每 5 秒采样，4 项健康检查，连续 3 次通过才提交），失败自动回滚到**独立记录的 last-known-good 镜像**（不从换装请求读，避免陈旧请求陷入回滚循环）。用户状态卷（会话、记忆、凭证、配置）挂载不动，换装后完整继承——用户体验到的是"更好的 agent"而非"被换掉的 agent"。

## 5. 实验结果全景：案例研究

四个 claweval 合规审计任务（SLA 合规审计中/英、补货链检查中/英），底座 OpenClaw + DeepSeek V3.2。基线均分 0.2526（0.75 及格线以下很远），典型失败：只列出部分工单、把其余标为"数据不完整无法判定"、偶尔张冠李戴客户名。

**MOSS 的单轮修复**：Locate 诊断出 harness 的工具结果中介（mediator）对某条通用执行路径没有注释分支 + 分发合成管线在 agent 把多个查询打包进单条 shell 时产出合并的、归属残缺的输出；Plan 给出双面修复——中介加注释分支（多实体载荷时注入显式用法提示）+ before-tool-call hook 链加预调用拒绝门（阻断批量 shell 模式，引导 agent 发独立可解析的调用）；Implement 落为单 commit：3 文件、+177/-1 行，含新中介测试文件。**模型与任务定义都没动，harness 改动是近因。**

结果：四任务均分 **0.2526 → 0.6100**（+0.357）；T138 冲到 0.9049（三次试验全过及格线）；SLA 对到 0.53-0.55（注释路径修掉最大缺陷，但逐工单时差算术与 SLA 分级有自身难度，一轮解决不了）。

## 6. 局限与批判性评价

**贡献是真实的**：这是第一个把"agent 改自己的 harness 源码"部署到带真实用户状态的生产基座上的完整系统。四件事在学术线全部缺位、在这里全部到位——失败证据自动策展（替代静态基准）、生产等价重放验证（替代单元测试）、用户批准门控（替代自动晋级）、健康探测回滚（替代不可逆修改）。小红书帖子"唯一覆盖生产部署的方案（失败集重放+批准/回滚门控）"的概括准确。

**"自我"改写的层级要看清**。MOSS 修改的是**底座**（OpenClaw）的 harness，MOSS 自己的进化机器（dispatcher、七阶段、裁决逻辑）不在可编辑范围内——与 DGM"开放探索循环固定不可自改"是同一个安全选择。所以严格说这是"进化引擎改宿主"而非"系统改自己"，自指程度比 DGM 低半级；换来的是生产可控性。这恰好实现了 DGM 安全章节设想的"系统中设置不可修改的部分"。

**评估侧的老问题换了个形态**。批次就是评估器：试用容器只重放**这一批**任务，没有全局回归套件——修好这 8 块的补丁是否在别处造成行为回归，只有健康探测（粗粒度）和回滚（事后）兜底。这是"评估器天花板"的生产版本：定向进化用局部具体性换掉了全局适应度的不可得，但局部锚定天然测不到锚外回归。关键点集在基线锁定、全循环不动——与 RQGM 的"epoch 内冻结评估器"是同一个手法（优化期间尺子必须冻结），但也继承同一个弱点：锁定的关键点集如果本身选偏，整个循环朝错误方向收敛。

**案例研究的证据强度有限**：单轮、四任务、用受控基准批次而非有机用户失败（作者自认"以真实性换可复现性"）；"无人工介入"的表述下，批准门在本次实验中被自动确认。deny gate 那类修复理论上 prompt 也能表达（"不要用批量 shell"），论文的回应是确定性 vs 遵守性——代码门 100% 生效，prompt 指令的生效率随模型波动，这个论证成立但案例里没有做"prompt 修复 vs 源码修复"的对照实验来量化差距。

**与六篇其他论文的关系**：DGM 证明源码自改在基准上有效，MOSS 证明它能在生产环境活下来；EvoLM/ECHO/RQGM/WGtG 在训练与评估循环里处理评估器进化，MOSS 把评估问题替换为"真实失败批次"——绕开了评估器塌缩，但引入了批次覆盖度问题。两条线互补：前者管"怎么保证改进是真的"，后者管"怎么把改进安全地交付给用户"。

## 7. 意义与位置

- Weng 框架对位：harness 优化（3 节）的生产化终点——workflow 设计、上下文工程、自改 harness 三条线在一个可部署系统里合流；她文中"生产系统需要 propose-verify-promote 门控"的原则在这里有最完整的实现。
- 对 Anthropic 文章的补充：Anthropic 讲前沿实验室内部的 RSI 闭环（改训练代码），MOSS 讲开源生态里应用层 agent 的 RSI 闭环（改 harness 代码）——层级不同，但"执行自动化+人类保留批准权"的治理结构完全同构。
- 后续可对接的方向：失败批次的自动策展（auto-scan 的 Task-Evaluate 判弱/缺失）本身是个静态评估器，若接入 WGtG 的锚定纪律或 EvoLM 的评估器共进化，可以补上"批次选择偏差"这一环。

**对安全治理五篇（报告 27）的开启**：MOSS 的批准/回滚门控是单系统实现；OpenLoopEvolve 把它协议化为版本血统 + Champion-Challenger；Falsifiable Release Gates 加上"收紧自动/放松人审/预测错自动关闭"的不变量——"门控"从一篇论文的设计选择变成可复用纪律的过程，起点是 MOSS。

**对 harness 工业化四篇（报告 13–16）**：Meta-Harness / Self-Harness / AutoSaddler 都在基准上进化 harness，MOSS 在生产流量上进化——四篇的接受门（proposer 隔离、双 split 回归、dev 门、用户批准）是同一纪律的四种形态；MOSS 独有的是"用户批准 + 健康探测回滚 + 用户状态卷不动"这三件生产专属部件。

**对 Prime Agent RCON 事故（报告 18）**：Prime Agent 的 refinement 版本化回滚只解决"改坏可撤"，不解决"改坏没被发现"；MOSS 的失败重放 + 用户批准门是"改坏必须被人看到"的设计——两者的差别正是"自动晋级"与"人审晋级"的差别。

**对 WikiSkill（报告 09）的分工**：MOSS 论证文本层够不着 harness 故障，WikiSkill 证明文本层内部还有大量收益且可跨模型交易——**结构性故障归源码层，流程性知识归文本层**；源码补丁绑定代码库不可迁移，文本技能可迁移是它相对源码层的独立优势。
